# 授权模型选型(访问控制模型:RBAC / ABAC / ReBAC …)

本文件是**模型选型层**的参考文档:先立判断轴,再逐个刻画主流访问控制模型的特性与适用边界,给出分层落地推荐,最后落到本项目当前的坐标与演进触发条件。

**它不重复实现层。** 本项目数据权限的**实现**决策已在别处钉死,本文只在末尾交叉引用:

- 实现层点决策 → `docs/adr/0001–0005`(policy 拆分、DataFilter 的 SQL-string seam、sdss 提到 ruoyi-api、跨 VT 红灯、OSS provider)。
- 数据权限术语表 → `ruoyi-common/ruoyi-common-mybatis/CONTEXT.md`。

选型原则:**没有"最好"的模型,只有"你的授权复杂度落在哪"与"模型原生擅长回答哪个问题"之间的匹配。** 所有推荐都从这个匹配推出,不以流行度为据。

---

## 一、判断轴(所有推荐从这里推)

真正的分水岭是这四条:

1. **授权复杂度长在哪?**
   - 长在**组织 / 岗位**("经理能审批")→ 角色驱动 → **RBAC**
   - 长在**资源归属与共享 / 层级**("我分享给你的这份""这个文件夹下的所有")→ 关系驱动 → **ReBAC**
   - 长在**上下文条件**("工作时间内""同部门""金额 < 1 万""密级 ≤ 我的许可")→ 属性驱动 → **ABAC**

2. **两个反向查询你需要哪个?**(最被低估,常直接定生死)
   - **"我能做什么?"**(前端渲染按钮 / 菜单)——RBAC 天然易;ABAC 天然难(决策是算出来的,枚举不出);ReBAC 中等。
   - **"谁能访问 X?"**(审计 / 合规 / 泄露排查)——ACL、ReBAC 天然易;RBAC 中等;ABAC 天然难。

   很多团队选了 ABAC 才发现前端渲染不出权限、审计答不出"谁能看"——就是没先问这条。

3. **强制点粒度:** API / 菜单 / 按钮(粗)vs 行 / 记录 / 字段(细)。同一系统常两层都要,而**同一个模型很难两层都做好**——这正是现实里几乎都分层混合的原因。

4. **谁维护规则、可否审计:** 规则写在代码(if/else)、配置(角色表)、还是独立策略引擎(policy-as-code)。**表达力越强的模型越难审计和推理**(策略互相干扰、隐性冲突)。

## 二、模型逐个刻画

### 2.1 根:ACL / DAC / MAC

| 模型 | 特性 | 推荐 / 别用 |
|---|---|---|
| **ACL** | 每资源挂 (主体, 权限) 表。答"谁能访问 X"极好,答"某人能干啥"极差,规模 O(主体×资源) 会爆。 | 资源少、授权稀疏、以资源为中心时(文件系统、对象存储桶策略)。业务系统里一般只作底层拼图。 |
| **DAC**(自主) | owner 决定给谁——Unix 权限位、分享链接的心智。 | 归属明确、由 owner 授予的场景。 |
| **MAC**(强制) | 系统按**安全标签 + 许可级**统一裁决,owner 无权推翻——Bell-LaPadula(保密:不上读、不下写)、Biba(完整性:反过来)、SELinux。 | 只在真有密级 / 强隔离合规需求时上;绝大多数业务系统不是 MAC,别硬套。 |

### 2.2 RBAC 家族(NIST 标准四级,务必分清)

- **RBAC0 核心 / 扁平**:User—Role—Permission 多对多 + 会话(session 可只激活部分角色)。Permission =(操作, 对象)。**一切的地基。**
- **RBAC1 层级**:角色继承,高阶自动含低阶权限(经理 ⊃ 员工)。
  - *推荐:* 组织**真有**嵌套资历层级、且低阶权限稳定被复用时才上。否则**扁平角色 + 组合**更好维护——继承会让"这角色到底能干啥"要顺链子推,反降可读性。**默认:先扁平,证明有复用痛点再引层级。**
- **RBAC2 约束**:职责分离(SoD)。
  - **静态 SSD**——不能同时**被授予**冲突角色(采购申请人 ≠ 审批人),授权时拦。
  - **动态 DSD**——可持有但同一会话不能同时**激活**,激活时拦。
  - 加基数约束(如 "CEO" 仅一人)。
  - *推荐:* 只在有合规 / 内控需求(财务、医疗、上市审计)时上,否则纯负担。
- **RBAC3**:RBAC1 + RBAC2 合体。

**根本特性:** 角色是 User 与 Permission 之间的**一层间接**,价值全在这层——在角色上管权限、把角色发给人,"这角色能干啥"一眼可查、可审计、贴合组织。

**死穴 = 角色爆炸。** 权限一旦要看**上下文**(自己的记录 vs 别人的、A 部门 vs B 部门、资源属性),纯 RBAC 没有"资源属性"和"用户与资源的关系"两个概念,只能靠造角色编码:`编辑_A部门`、`编辑_B部门`、`编辑_仅本人`……组合式膨胀。**本项目的 DataScope 就是给 RBAC0 打的这块补丁**(详见 §4)。

### 2.3 ABAC(属性驱动)—— NIST SP 800-162

- **特性:** 决策 = f(主体属性, 资源属性, 动作属性, 环境属性) 对**策略规则**求值。例:`allow if user.dept == res.dept and action == 'read' and env.time ∈ 工作时间 and user.clearance >= res.level`。表达力最强——能把 RBAC、MAC、归属、时间、IP 全编码进去(角色不过是一个属性),故理论上 **RBAC ⊂ ABAC**。
- **强项:** 无角色爆炸、上下文感知、细粒度、策略集中。
- **弱项(选它前必须认):**
  - **反向枚举难**——答不好"某人能访问什么"(决策是算出来的),伤前端渲染、伤"谁能看 X"审计。
  - **难推理难审计**——策略一多会互相干扰、隐性冲突。
  - **属性供给与新鲜度**——决策时得拿齐相关属性,属性从哪来、够不够新是真问题。
- **推荐:** 授权复杂度确实长在"上下文条件"、且能接受反向查询变难时。**别用**在只是想解决"哪些行"却其实是关系问题的场景(那是 ReBAC 的活)。

### 2.4 ReBAC(关系驱动)—— Google Zanzibar 一脉

- **特性:** 能否访问取决于主体与对象的**关系图**:"你能看文档 X,若你是 X 的 editor,或你属于某个是 X 的 viewer 的组,或你是包含 X 的文件夹的 viewer"。权限沿**归属、成员、包含 / 层级、分享**传播。
- **强项:** **三个查询全好**——"某人能否访问 X""谁能访问 X""某人能访问哪些"都能靠图的正 / 反向索引高效答;天生适合**分享 / 层级 / 协作 / 多租户文档**;有一致性模型(Zanzibar 的 zookie)解决"分享刚撤销就被旧快照放行"的 new-enemy 问题。
- **弱项:** 要**维护关系元组**(写时成本、让图与领域数据同步);对**纯上下文条件**(时间、IP)不自然——现代实现靠 OpenFGA conditions / SpiceDB caveats 在关系上叠属性条件补足;小系统是杀鸡用牛刀。
- **推荐:** Google Drive 式分享、团队 / 文件夹层级、SaaS "谁把什么共享给了谁"——ReBAC 主场;用 RBAC 做会角色爆炸,用 ABAC 做会反向查询答不出。

### 2.5 策略引擎 / PBAC / policy-as-code,与"正确但冷门"的 NGAC

- **PBAC:** 常与 ABAC 混用,重点在**架构**而非数学模型——把授权逻辑抽到独立**策略决策点(PDP)**,与应用解耦(XACML 的 PEP / PDP / PAP / PIP 四件套)。现代形态是**策略即代码**(OPA/Rego、Cedar、Oso)。价值是**解耦 + 可测试 + 集中治理**,可承载 RBAC / ABAC / ReBAC 任意一种。**别过早上 PDP**——逻辑没超出代码里几行 if/else 时,引入 PDP 是纯复杂度。
- **NGAC**(NIST SP 800-178):XACML 的接班方案,用**属性图 + 策略机**建模,比 XACML 更能高效回答审查类查询、表达力也强。生态小、工具少,但模型设计更干净——**当心智模型值得知道,落地成熟度不如 §5 几个。**

### 2.6 正交维度(别与上面的模型混为一谈)

- **claims / scope(OAuth2 / OIDC):** JWT 里带 scope(`read:orders`)、roles、groups。这是**授权决策 / 属性怎么在服务间传输**,不是决策模型本身——仍需 RBAC / ABAC / ReBAC 定义 claims 的含义。**关键澄清:OAuth scope ≠ 用户权限**,scope 是"客户端 App 被授权代表用户做什么"(委托授权),两者常被搞混。
- **capability(能力安全):** 权限 = 持有不可伪造的**能力令牌**,它同时指明资源并授予操作(签名 URL、macaroon、API key)。无环境权限、天然最小授权、避免 confused-deputy。**作局部机制**(分享链接、下载直链、服务间委托),极少作整系统主模型。

## 三、对比表

| 模型 | 原生擅长的问题 | "我能干啥"反查 | "谁能访问 X"反查 | 主要死穴 | 推荐场景 |
|---|---|---|---|---|---|
| ACL | 单资源谁有权 | 差 | 好 | 规模爆炸 | 资源少、资源为中心 |
| RBAC0/1 | 某类人能做什么操作 | **好** | 中 | 上下文一来就角色爆炸 | 组织 / 岗位驱动的粗粒度 |
| RBAC2 | 同上 + 职责分离 | 好 | 中 | 无合规时纯负担 | 财务 / 医疗 / 审计内控 |
| ABAC | 给定上下文此刻是否允许 | **差** | 差 | 反查难、难审计、属性供给 | 复杂度长在上下文条件 |
| ReBAC | 关系图上是否连通 | 中 | **好** | 要维护关系元组 | 分享 / 层级 / 协作 / 多租户文档 |
| PBAC / 引擎 | (承载上面任意一种) | 取决于承载模型 | 同 | 过早引入 = 纯复杂度 | 逻辑超出 if/else、要集中治理 |

## 四、分层落地推荐(正解不是选"一个"模型)

**按两层强制点分层组合——这不是折中,是正解:**

1. **粗粒度层(API / 菜单 / 按钮)= RBAC0,慎用 RBAC1。** User→Role→权限串,前端靠它渲染("我能干啥"天然好答)。**默认扁平角色 + 组合**;组织真有稳定资历继承、且验证到复用痛点,才升 RBAC1。RBAC2 留给有合规需求时。

2. **细粒度层(哪些行 / 记录)= 看复杂度性质二选一:**
   - 判定靠**资源属性**(部门 / 地区 / owner 字段 / 密级)→ **ABAC 式谓词**:把策略编译成注入查询的 `WHERE` 条件。
   - 判定靠**关系**(共享给谁、团队成员、文件夹层级)→ **ReBAC**,别用属性谓词硬缝(会重演爆炸)。

3. **策略引擎(PDP)何时上:** 当第 2 步规则从"几条"长到"一堆、还要被非工程同事改、还要能单测和审计"时,才抽成 policy-as-code。**不到那天不上。**

## 五、本项目落点与演进触发

**当前坐标 = RBAC0(粗)+ DataScope(细,ABAC 谓词式,含 dept 层级的 ReBAC 味道)。**

- **粗粒度层:** Sa-Token 的 `@SaCheckPermission` / `@SaCheckRole`,标准 **RBAC0**(user→role→权限串)。这是主流意义上的 RBAC,不是"非 RBAC"。
- **细粒度层:** `@DataPermission` + `PlusDataPermissionInterceptor` 的**数据权限**,本质是 **ABAC 谓词注入**——policy 由授权快照(user 的 dept / role + scope 类型)算出一个谓词(`dept_id IN (...)` / `dept_id = x` / `user_id = self`)AND 进 SQL。其中 `DEPT_AND_CHILD*` 三档经 `sdss` 展开**部门树**,是沿**包含层级**传播的 **ReBAC 味道**;`DEPT` / `SELF` 两档是纯属性谓词。术语精确定义见 `CONTEXT.md`。

**这块坐标是自洽的**,而 `docs/adr/0001–0005` 正在做的深化,恰好就是 §4 推荐的**"策略 → 查询谓词"干净 seam**:

- `policy` 成为纯函数 `(声明, 授权快照, 操作类型) → DataFilter` —— 见 ADR 0001。
- `DataFilter` 三态(`UNRESTRICTED` / `DENY` / `Predicate`),谓词载荷是 SQL 文本 —— 见 ADR 0002。
- 范围展开器 `sdss` 以类型化 SPI 发布到 `ruoyi-api`,policy 脱离静态 Spring 容器 —— 见 ADR 0003。

**演进触发条件(什么信号该换档,而非拍脑袋):**

| 信号 | 含义 | 动作 |
|---|---|---|
| "哪些行"始终由**部门 / 属性**判定 | 仍在 ABAC 谓词的舒适区 | 保持方向,只把 policy→predicate 的 seam 做干净(即 ADR 0001–0003 在做的),**不必换模型**。 |
| 出现**跨部门分享 / 显式授予 / 协作**("把这条记录单独授权给某人 / 某组") | 授权不再能从 dept 树推导出,变成**关系** | 这是引入 **ReBAC** 的信号——别在 DataScope 上加参数硬缝。 |
| 出现**上下文条件**(时间、状态机阶段、金额阈值) | 属性维度增多 | policy 内扩 ABAC 属性;规则膨胀到非工程要改时再考虑 §4-3 的 PDP。 |
| SoD / 双人复核合规需求 | 需职责分离 | 上 **RBAC2**(SSD / DSD)。 |

**跨虚拟线程的上下文传播是已知缺陷、故意留红**(ADR 0004),不要在演进时顺手"修绿"——那是独立工单。

## 六、工具选型(按契合度,不按热度)

| 工具 | 模型 | 特性 | 何时选 |
|---|---|---|---|
| **Sa-Token**(现用) | RBAC 注解式 | 轻量、注解驱动;细粒度得自己写 | 现状——DataScope 正是自己写的那部分 |
| **Casbin** | RBAC / ABAC / 类 ReBAC | PERM 元模型,一套配置多模型,轻量可嵌 JVM | 从硬编码毕业时的务实首选 |
| **Cedar**(AWS,Rust) | RBAC + ABAC | 专为授权设计,**可做策略静态分析 / 验证** | greenfield、看重可分析性 |
| **OpenFGA / SpiceDB** | ReBAC(Zanzibar) | 专用授权库 + 关系元组存储 | 分享 / 层级重的系统 |
| **OPA / Rego** | 通用策略引擎 | 微服务 / 基础设施 / K8s 强,Rego 有学习曲线 | 需要解耦 PDP、跨服务统一策略 |
| **Oso / Polar** | ReBAC 友好 | 嵌入式、逻辑语言 Polar | app 内嵌、关系为主 |

## 七、一句话决策规则

先问 **"授权复杂度长在组织、关系、还是上下文"**,再问 **"我更需要答'我能干啥'还是'谁能访问 X'"**——这两个答案基本把模型定死,剩下的都是实现载体。
