# RuoYi-Vue-Plus 测试规范

> 适用范围：本仓库（Spring Boot 4.0.6 / Java 21 / MyBatis-Plus + dynamic-datasource / Sa-Token / Redisson / warm-flow）。
> 核心立场：**业务型系统以"全量 `@SpringBootTest` + 真实容器"的集成测试为主**，隔离单测仅用于纯函数 / 工具类。
> 维护原则：**只写代码 / pom / git 读不出来的东西**——为什么这样测、踩过的坑、不直观的框架机制。**不复制既有实现源码**（如 `TestcontainersBase`，以磁盘 `ruoyi-admin/src/test` 为准，避免漂移）；**示范模板是例外**——§5 的测试骨架 / Sa-Token mock 模板用于演示不直观的写法，可保留，但只示范、标出处、不与磁盘逐行同步。改基建必须同步改本文。

---

## 0. 速查（新增一个集成测试只需 3 步）

1. 在 `ruoyi-admin/src/test/java/org/dromara/test/<领域>/` 下新建 `XxxIntegrationTest`，`extends TestcontainersBase`，加 `@Tag("dev")`、`@ActiveProfiles({"dev","test"})`、`@SpringBootTest`。
2. `@Autowired` 注入要测的 Mapper / Service；涉及登录态或数据权限的，套用 [§5.2](#52-涉及登录态--数据权限的测试) 的 Sa-Token mock 模板。
3. 运行（需 Docker daemon）：
   ```bash
   sh ./mvnw -pl ruoyi-admin test -DskipTests=false -Dtest=XxxIntegrationTest
   ```
   或在 IntelliJ 里直接运行该类（开发回路最顺，IDEA 忽略 surefire 的 `<groups>` 过滤）。

> ⚠️ 提交前自检（兼最易忘点）：① 三件套注解齐全——不加 `@Tag("dev")` 在 Maven 下**不会执行**（[§6.2](#62-tag-与-surefire-groups-机制必须理解)）；② 改过上游源码先 `install` 刷新本地仓库，否则假绿（[§7](#7-避坑清单-gotchas) #8）；③ 断言要"拦截器失效则会失败"才有意义（§5.4）；④ Docker daemon 在跑，且 `-DskipTests=false` 本地跑绿。

## 1. 测试哲学（为什么这样测）

- **隔离单测在业务型系统里信号量低**：本系统绝大多数代码是"取参 → 调框架 → 落库"的编排，把依赖全 mock 掉只是在验证 mock 自己，几乎不抓真实缺陷，且与实现强耦合、重构即碎。
- **真正的风险集中在横切与"框架魔法"上**——这些东西看不见、最容易悄悄坏：
  - **数据权限**（`@DataPermission` + MyBatis 拦截器按部门 / 角色重写 SQL）
  - **SQL 方言**（`find_in_set` vs `strpos`、分页、`bigint`/`sysdate()` 等 MySQL/PG 差异）
  - **状态机**（工作流驳回 / 锁定审批人等）
  - **缓存 / 序列化 / 多数据源路由 / 拦截器链顺序**
- **结论**：默认写**集成测试**——启动整个 `DromaraApplication`、连真实 MySQL + Redis 容器，断言端到端行为。这是唯一能覆盖上述"框架魔法"的层次。

> 反面教材（**禁止**）：用 `@MockBean` 把 Mapper / 拦截器 mock 掉来"测"数据权限——这恰好绕过了被测对象，等于没测。

## 2. 测试分层与选型

| 层次 | 何时用 | 上下文 | 例子 |
|---|---|---|---|
| **集成测试（默认主力）** | 任何经过框架链路的行为：数据权限、联表、方言、状态机、缓存、序列化 | 全量 `@SpringBootTest` + Testcontainers（MySQL+Redis） | `DataPermissionIntegrationTest` |
| **纯单元测试（少量）** | 无 Spring 依赖的纯函数 / 工具类 / 算法 / 校验逻辑 | 无 Spring 上下文 | `AssertUnitTest`、`ParamUnitTest` |

选型判据一句话：**只要断言依赖"框架做了什么"，就写集成测试；只要被测逻辑是纯输入输出，就写纯单测。** 中间形态（部分 mock 的"伪集成"）不写。

## 3. 目录结构与命名约定

- **位置统一在 `ruoyi-admin/src/test`**：全量上下文需要完整的模块依赖（system / workflow / ai 等都在 admin 聚合），放这里才能 `@SpringBootTest` 启动整个应用。
  - 业务模块（如 `ruoyi-system`）自身**不**放需要全量上下文的集成测试。
- **包名**：`org.dromara.test.<领域>`，按被测能力分包：
  - `org.dromara.test.container` —— 基建（容器基类），**不要**往里塞用例。
  - `org.dromara.test.datapermission`、`org.dromara.test.workflow` …… —— 按领域分。
- **类名**：集成测试 `*IntegrationTest`；纯单测 `*UnitTest`（沿用仓库既有命名）。
- **必加注解三件套**（集成测试）：`@Tag("dev")`、`@ActiveProfiles({"dev","test"})`、`@SpringBootTest`，并 `extends TestcontainersBase`。
- **`@DisplayName`** 建议加（仓库既有单测均带中文 `@DisplayName`，便于报告阅读）。

## 4. 集成测试基建

### 4.1 依赖（`ruoyi-admin/pom.xml`，test scope）

三个 Testcontainers artifactId，版本由 spring-boot-dependencies BOM 管理（TC 2.0.5）：`testcontainers`（核心，供 `GenericContainer` 跑 Redis）、`testcontainers-mysql`（TC 2.x 新名，含 `MySQLContainer`）、`testcontainers-junit-jupiter`。

> Redis 直接用 TC core 的 `GenericContainer(redis:8.6.3-alpine)`（对齐 `script/docker/docker-compose.yml` 生产镜像），**不**额外引入 `com.redis:testcontainers-redis`（省依赖、离线可用）。
> ⚠️ TC 2.x 已重命名 artifactId：用 `testcontainers-mysql` / `testcontainers-junit-jupiter`（**不是** 1.x 的 `mysql` / `junit-jupiter`）。

### 4.2 `TestcontainersBase`：容器单例 + 接线 + schema

位置：`ruoyi-admin/src/test/java/org/dromara/test/container/TestcontainersBase.java`（**实现以磁盘为准**）。所有集成测试 `extends` 它。关键设计（**改动需谨慎**）：

- **单例启动、不 `stop()`**：`static {}` 块启动一次，交 Ryuk 回收；配合 `.withReuse(true)` + 本机 `~/.testcontainers.properties` 的 `testcontainers.reuse.enable=true` 跨轮复用，大幅提速。
- **用 `@DynamicPropertySource` 而非 `@ServiceConnection`**：后者只能绑定标准前缀 `spring.datasource.*`，**命中不了** dynamic-datasource 的自定义前缀 `spring.datasource.dynamic.datasource.master.*`。注入项含 master 的 url/username/password/driver、`spring.datasource.dynamic.p6spy=false`、redis 的 host/port/password。
- **schema 直接读仓库内 `script/sql/ry_vue.sql`（不拷贝、不 fork）**：用 Spring `ScriptUtils.executeSqlScript` 跑 `FileSystemResource`，避免与框架升级产生漂移；路径对 `../script/sql`（surefire/IDEA cwd = 模块目录）与 `script/sql`（仓库根 cwd）做双重兜底，失败日志打印 `getAbsolutePath()`。
- **MySQL `mysql:8.4`**（DDL 为 MySQL 8 编写）；**Redis 必须设密码**（`--requirepass` 且 `spring.data.redis.password` 与之相等，见 [§7](#7-避坑清单-gotchas) #2）。

### 4.3 profile：`@ActiveProfiles({"dev","test"})` + `application-test.yml`

- **继承 `application-dev.yml`** 的全部 `enabled:false` 开关与 `redisson` 块，`test` profile 只做**极少量**覆盖。
- 连接坐标**不写死在 yml**，由 `TestcontainersBase` 的 `@DynamicPropertySource` 动态注入。
- 当前 `ruoyi-admin/src/test/resources/application-test.yml` 仅覆盖：`spring.datasource.dynamic.p6spy=false`（避免 p6spy 包装容器 URL）、`spring.ai.mcp.server.enabled=false`、`captcha.enable=false`。

> ⚠️ **不要**在 test profile 里关 `snail-ai.open-api`——会缺 bean 导致启动失败（见 [§7](#7-避坑清单-gotchas) #3）。

### 5.2 涉及登录态 / 数据权限的测试

数据权限链路：`@DataPermission` 切面 → `DataPermissionHelper.getVariable("user")` → `SaHolder.getStorage()`。
本项目运行期是 **Sa-Token ThreadLocal 上下文**（`SaTokenContextFilterForJakartaServlet` 每请求初始化），MOCK 测试不经该 filter，**必须手动初始化 Sa-Token mock 上下文**，否则抛「SaTokenContext 上下文尚未初始化」。

> 注意：初始化 Sa-Token 上下文**靠 `setModelBox`，不是**绑 `MockHttpServletRequest`（计划初版的错误假设）——后者对"初始化 Sa-Token 上下文"无效。但**测超管短路**时另需绑定 `MockHttpServletRequest`（用途不同：喂登录成功监听器，见 [§5.2.1](#521-测超管短路与过滤相反必须真登录)）。

标准模板（摘自 `DataPermissionIntegrationTest`）：

```java
@BeforeEach
void initSaTokenContext() {
    SaTokenContextForThreadLocalStaff.setModelBox(
        new SaRequestForMock(), new SaResponseForMock(), new SaStorageForMock());
}

@AfterEach
void clearSaTokenContext() {
    SaTokenContextForThreadLocalStaff.clearModelBox();
}

/** 精确控制数据权限计算所需的 userId / deptId / 角色范围 */
private void loginAs(Long userId, Long deptId, Long roleId, String dataScope) {
    LoginUser loginUser = new LoginUser();
    loginUser.setUserId(userId);
    loginUser.setDeptId(deptId);
    loginUser.setUserType("sys_user");
    RoleDTO role = new RoleDTO();
    role.setRoleId(roleId);
    role.setDataScope(dataScope);          // "1"全部 / "4"本部门及以下 / "5"仅本人 …
    loginUser.setRoles(List.of(role));
    DataPermissionHelper.setVariable("user", loginUser);   // 预置即可，无需真实 StpUtil.login / Redis
}
```

要点（已核实）：
- 直接 `setVariable("user", loginUser)` 即可，**无需**真实登录 / 写 Redis。
- **测数据权限过滤时**用**普通 `LoginUser`**（不调 `StpUtil.login`）：`isSuperAdmin()` 取不到 userId → false，**不会**走超管短路，才能真实触发过滤。（**反过来测超管短路**见 [§5.2.1](#521-测超管短路与过滤相反必须真登录)。）
- mock 请求下取不到 `HandlerMethod` → `currentAccess()` 返回 `EMPTY` → 不做权限位过滤，使用 `user.getRoles()` 全部角色。因此注入**单个 `RoleDTO`（仅 `roleId` + `dataScope`，无需 `roleKey`）**即被采用，单表 `selectPageUserList` 与别名 join `selectAllocatedList` 同理。
- **要测"接口权限约束选角色"本身**（生产里 `@SaCheckPermission` 经 `resolveAccess` 把 perms 喂给 `scopeRoles`，仅 `dataScopeRoleMap.get(perm)` 命中的角色参与计算）：**不必起 MockMvc / 伪造 `HandlerMethod`**，直接用核心公共 API `DataPermissionHelper.setAccess(new DataPermissionAccess(perms, roleKeys))` 预置约束——`currentAccess()` 见非空 access 即返回、跳过 HTTP 解析路径。再给 `LoginUser` 设**多角色 + `setDataScopeRoleMap(perm→roleId)`**，即可断言"只有被 perm 选中的角色生效"（见 `AccessScopedRoles`：ALL+SELF 两角色但 perm 只授 SELF → 仅 SELF 过滤、结果空；若选角色回退把 ALL 漏进来则返回全量、用例失败）。`setAccess` 与 `setVariable` 同写入每用例新建的 `SaStorageForMock`，用例间天然隔离，无需额外清理。
- **多 scope 用例可用 `@Nested` 分组**（如按"单表 / 别名 join / 超管"分组），共享 `@BeforeEach` 与 helper；JUnit 5 外层 `@BeforeEach` 对 `@Nested` 同样生效。

### 5.2.1 测超管短路（与过滤相反：必须真登录）

`PlusDataPermissionHandler` 开头 `if (LoginHelper.isSuperAdmin()) return where;` 直接放行；`isSuperAdmin()` **只认 Sa-Token `getUserId()`**（读 token 的 `USER_KEY` extra），**与注入的 `DataPermissionHelper` 变量无关**。所以测这条安全攸关旁路必须**真登录**为超管（`SystemConstants.SUPER_ADMIN_USER_ID = …001`）。

坑 1（同步 NPE）：真登录会触发 Sa-Token 登录事件 → `UserActionListener` → `UserLoginSuccessListener`（同步 `@EventListener`），后者 `ServletUtils.getRequest().getHeader("User-Agent")` 解析 UA，MOCK 无请求会抛 NPE。故须**绑定带 `User-Agent` 头、内网 `remoteAddr` 的 `MockHttpServletRequest`**（内网 IP 让 `AddressUtils` 不联网）。该同步监听器里的 `updateLastLoginInfo`（主线程、本事务内）由 `@Transactional` 回滚；`@AfterEach` 须 `StpUtil.logout()` + `RequestContextHolder.resetRequestAttributes()`（登录态在 Redis，不随事务回滚）。

坑 2（异步脏数据，易漏）：上面的同步监听器还会 `recordLoginInfo` → 发 `LoginInfoEvent` → `SysLoginInfoServiceImpl.recordLoginInfo`（`@Async @EventListener`）在**独立线程、无事务**地向 `sys_login_info` 物理插一行 `user_name='admin'`，**不在测试线程的事务里 → 不被 `@Transactional` 回滚**，会污染 Testcontainers MySQL。清理**不能放 `@AfterEach`**（仍处于测试事务内，且 MySQL 默认 REPEATABLE READ 快照看不到异步新提交的行——既删不到、删了也随事务回滚），须放 **`@AfterTransaction`**（事务结束后、事务外执行，Mapper 调用自动提交）：先 `Awaitility` 有界轮询等该行出现（异步有时序竞态、超时容忍），再物理删除（`SysLoginInfo` 非 `@TableLogic`，`delete(Wrapper)` 为真删）。

```java
@Test
@Transactional
void superAdmin_shortCircuit() {
    loginAs(USER_TEST1, DEPT_CHANGSHA, ROLE_SELF, "5");   // 注入一个本应过滤到空的 scope
    MockHttpServletRequest req = new MockHttpServletRequest();
    req.addHeader("User-Agent", "Mozilla/5.0 (Test)");
    req.setRemoteAddr("127.0.0.1");
    RequestContextHolder.setRequestAttributes(new ServletRequestAttributes(req));
    LoginUser su = new LoginUser();
    su.setUserId(SystemConstants.SUPER_ADMIN_USER_ID);
    su.setUserType("sys_user");
    su.setUsername("admin");
    LoginHelper.login(su, null);                          // 单一重载 login(LoginUser, SaLoginParameter)，null 内部兜底
    // 短路生效：注入的限制性 scope 被忽略，返回全部
    assertThat(pageUserNames()).containsExactlyInAnyOrder("admin", "test", "test1");
}
// @AfterEach: StpUtil.logout(); RequestContextHolder.resetRequestAttributes();
// @AfterTransaction: await sys_login_info(user_name='admin') 出现后物理删除（异步写逃逸事务，须事务外清理）
```

### 5.3 Mapper / 依赖注入方式

- **用 `@Autowired` 字段注入**（Mapper 由 `@MapperScan` 动态注册为 bean，运行期正常）。
- **不能**照搬业务代码的 `@RequiredArgsConstructor` 构造注入：Spring 测试构造注入默认关闭，会抛 `No ParameterResolver registered for ... constructor`（除非额外加 `@TestConstructor(autowireMode = ALL)`）。
- **IDEA 误报**：字段注入 Mapper 会被静态检查标红 "No beans of 'XxxMapper' type found"，运行期无误。已验证：装 MyBatisX、加 `@SuppressWarnings(...)` 均**不能**消除该误报。最干净的处理是把该 inspection 的 severity 调低（零代码改动），用一行注释说明即可，**不要**为此去改上游框架 Mapper 的生产代码。

### 5.4 断言与种子数据约定

- **种子数据来源唯一**：`script/sql/ry_vue.sql`，断言基于其中**稳定的固定 ID**，不要依赖自增 / 时间。
- **断言库统一用 AssertJ**（`assertThat(...).containsExactlyInAnyOrder(...)` / `.isEmpty()` / `.doesNotContain(...)`）。
- **设计"会失败才有意义"的断言**：例如数据权限用例，若拦截器没生效会返回全量，则 `本部门及以下` 与 `仅本人` 必然失败——它们通过，才证明 SQL 被真实改写。分页 join 用例额外断言 `page.getTotal()`，才是 COUNT 改写的探针（基线 3 → 改写后应为 2/0）。
- **只读 vs 可变数据（防种子膨胀）**：只读的结构性断言可依赖 `ry_vue.sql` 这个不可变共享夹具；**需要可变业务行的用例必须用例内自造 + `@Transactional` 回滚**，**不要**往 `ry_vue.sql` 加场景数据（否则种子越滚越大、用例互相耦合、缺数据即报错）。例：CUSTOM(2) 数据范围依赖 `sys_role_dept` 行（种子无），故用例内 `sysRoleDeptMapper.insert(...)` 造、`@Transactional` 回滚（`SysRoleDept.roleId` 是 `@TableId(IdType.INPUT)`，须显式 set）。
- **`@Cacheable` 不随事务回滚**：`@sdss.getRoleCustom(roleId)` / `getDeptAndChild(deptId)` 结果缓存在 Redis（`@Transactional` 只回滚 MySQL）。用例内造 `sys_role_dept` 后须先 `CacheUtils.evict(CacheNames.SYS_ROLE_CUSTOM, roleId)` 再查，且用**专用 roleId**（种子无 `…002`）避免跨用例 / 跨轮缓存污染。
- 常用种子（节选）：部门树 长沙分公司`…102` 下挂 市场`…108`/财务`…109`（`…108`/`…103` 为叶子）；用户 `admin/…001`、`test/…003`、`test1/…004`（`create_by` 均为 `…001`）；角色 全部(1)/本部门及以下(4)/仅本人(5)；`sys_role_dept` 零种子行。`SUPER_ADMIN_USER_ID` = `admin/…001`。

## 6. 运行测试

### 6.1 环境前置（本机）

- **JDK**：高版本 JDK 直接跑即可（pom `release=21` 编译出 release-21 字节码），不用 jenv、不必设 `JAVA_HOME`/切 JDK 21（详见 `本机环境与构建.md`）。
- **`mvnw` 无执行权限**：一律 `sh ./mvnw ...`。
- **Docker daemon 必须运行**（Testcontainers 依赖）。
- **把多模块装进本地仓库**（reactor 模块未预装）：**首次、以及之后每次改动上游 `ruoyi-common-*` / `ruoyi-modules/*` / `ruoyi-api` 源码后都要重跑**，否则 §6.3 不带 `-am` 的 `test` 会用旧 jar 假绿（原理见 [§7](#7-避坑清单-gotchas) #8）：
  ```bash
  sh ./mvnw -pl ruoyi-admin -am install -DskipTests
  ```

### 6.2 `@Tag` 与 surefire `<groups>` 机制（必须理解）

根 `pom.xml`：`<skipTests>true</skipTests>`，且 surefire `<groups>${profiles.active}</groups>` / `<excludedGroups>exclude</excludedGroups>`，`profiles.active` 默认 = `dev`。**含义**：

1. Maven 默认 `skipTests=true`，跑测试必须显式 `-DskipTests=false`。
2. surefire 只执行 `@Tag` 等于当前 profile（默认 `dev`）的用例 → **集成测试必须 `@Tag("dev")` 才会被 Maven 执行**。
3. `@Tag("exclude")` 的用例永远被排除。
4. **IntelliJ 直接运行类时忽略上述 `<groups>` / `<skipTests>`**，所以开发回路用 IDE 最顺。

### 6.3 命令

```bash
# 跑单个集成测试类（前提：已装上游 jar 与工作区一致；改过上游源码先按 §6.1 重装）
sh ./mvnw -pl ruoyi-admin test -DskipTests=false -Dtest=DataPermissionIntegrationTest
```

> ⚠️ 跑单测**不要加 `-am`**：`-am` 会把上游模块拉进 `test` phase，撞上 `ruoyi-common-mybatis` 等无 JUnit 5 引擎的硬失败；但不带 `-am` 又不会重编上游源码，故改过上游必须先按 §6.1 单独 `install`。完整原理见 [§7](#7-避坑清单-gotchas) #8。

### 6.4 提速：容器复用

`~/.testcontainers.properties` 写入 `testcontainers.reuse.enable=true`，配合基类已设的 `.withReuse(true)`，容器跨测试轮复用（二次运行约 15s 量级）。

## 7. 避坑清单（Gotchas）

实施中踩过、已修复并固化为规范，**新增 / 改基建时逐条对照**：

| # | 坑 | 现象 | 正确做法 |
|---|---|---|---|
| 1 | **TC 2.x `MySQLContainer` 非泛型** | `类型...不带有参数` 编译失败 | `new MySQLContainer(...)`，**无 `<>`**；artifactId 用 `testcontainers-mysql` |
| 2 | **Redis 必须设密码** | `ERR AUTH ... without any password configured` | 容器 `--requirepass <pwd>` 且 `spring.data.redis.password` 与之相等（空密码也会触发 AUTH） |
| 3 | **snail-ai.open-api 不能在 test 关** | `No qualifying bean 'OpenApiAgentClient'` 启动失败 | 继承 dev（默认 `true`），`SnailAiController` 无条件注册却依赖该 bean；启动无外连不影响 |
| 4 | **Sa-Token 上下文是 ThreadLocal 版** | `SaTokenContext 上下文尚未初始化` | 用 `SaTokenContextForThreadLocalStaff.setModelBox(new SaRequestForMock(), ...)` 初始化；绑 `MockHttpServletRequest` 对"初始化 Sa-Token 上下文"无效（但真登录测超管时另需绑它喂登录监听器，见 [§5.2.1](#521-测超管短路与过滤相反必须真登录) / #9） |
| 5 | **schema 路径随工作目录变化** | `加载 ry_vue.sql 失败` | 基类已做 `../script/sql` 与 `script/sql` 双重兜底，失败日志打印 `getAbsolutePath()` |
| 6 | **p6spy 包装容器 URL** | 连接异常 | test 下 `spring.datasource.dynamic.p6spy=false` |
| 7 | **测试构造注入** | `No ParameterResolver registered for ... constructor` | 用 `@Autowired` 字段注入，别照搬 `@RequiredArgsConstructor` |
| 8 | **`-am` + `test` 跑上游测试** | 上游 `ruoyi-common-mybatis` 报 `groups/excludedGroups require ... JUnit 5`（硬失败） | 跑单测**不加 `-am`**；但不带 `-am` 不会重编上游源码，故**上游未装或源码已变更**都要先单独 `install -DskipTests`（`-am` 仅 install 阶段安全，因其 `-DskipTests` 跳过上游测试）刷新本地仓库再跑，否则旧 jar 假绿 |
| 9 | **真登录触发登录成功监听器** | 测超管 `LoginHelper.login` 抛 `Cannot invoke UserAgent.getBrowser() ... null`（`UserLoginSuccessListener` 解析 UA） | 绑定带 `User-Agent` 头 + 内网 `remoteAddr` 的 `MockHttpServletRequest`；`@Transactional` 回滚其 `updateLastLoginInfo` DB 写入；`@AfterEach` `StpUtil.logout()` + `RequestContextHolder.resetRequestAttributes()`（见 [§5.2.1](#521-测超管短路与过滤相反必须真登录)） |
